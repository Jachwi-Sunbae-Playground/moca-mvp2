# 이슈와 PR

## 이슈

### 제목

```text
[파트][작업 종류] 작업 내용
```

예시:

```text
[BE][FEAT] 지원 자격 조회 기능 구현
[BE][FIX] 매물 목록 중복 조회 문제 수정
[BE][REFACTOR] 지원 정책 조회 책임 분리
```

### 본문

```markdown
## 배경
<!-- 이 작업이 필요한 이유와 해결하려는 문제를 작성 -->

## 작업 내용

구현해야 할 내용을 작성합니다.

- [ ] 

## 완료 조건

작업이 완료됐다고 판단할 수 있는 기준을 작성합니다.

- [ ] 

## 참고 자료

관련 문서, 정책 출처, 디자인, API 명세 또는 선행 Issue를 연결합니다.

- 관련 문서:
- 선행 Issue:
- 후속 Issue:
```

이 양식은 [`.github/ISSUE_TEMPLATE/issue.md`](../../.github/ISSUE_TEMPLATE/issue.md)에 등록되어 있어 Issue를 생성하면 자동으로 채워진다. 양식을 바꾸면 이 문서와 템플릿 파일을 같은 PR에서 수정한다.

## PR

- PR에는 변경 목적, 주요 설계 결정, 테스트 결과, Swagger 변경 사항을 명시한다.
- 하나의 PR에는 하나의 목적만 담는다.
- 작업 브랜치의 코드는 PR을 통해 `develop` 브랜치로 병합한다.
- 운영 배포는 `develop`에서 `main`으로 **승격 PR**을 열어 진행한다. 승격 PR 제목은 `[ALL][Chore] develop을 main으로 승격한다` 형식을 사용하고, 본문에 이번 배포에 포함되는 변경을 적는다.
- AWS 콘솔 작업처럼 diff가 없는 작업은 PR로 만들지 않고 이슈 체크리스트로 진행한다. 배포 설정·파이프라인 정의처럼 저장소에 파일이 들어가는 작업은 PR로 리뷰한다.

### 제목

```text
[파트][작업 종류] 작업 내용
```

예시:

```text
[BE][Feat] 예약 생성 기능을 구현한다
[BE][Fix] 중복 예약이 생성되는 문제를 수정한다
[BE][Refactor] 예약 검증 책임을 분리한다
```

### 본문

```markdown
## 🔗 관련 이슈
<!-- 이 PR이 해결하는 이슈 -->
Related to #

## 작업 내용

- 구현하거나 변경한 내용을 작성합니다.

## 고민한 점

- 구현 과정에서 고민한 부분과 선택 이유를 작성합니다.

## 리뷰 요청 사항

- 중점적으로 봐주었으면 하는 부분을 작성합니다.

## 테스트

- [ ] 기존 테스트가 통과합니다.
- [ ] 변경 사항에 대한 테스트를 작성했습니다.
```

이 양식은 [`.github/pull_request_template.md`](../../.github/pull_request_template.md)에 등록되어 있어 PR을 생성하면 자동으로 채워진다. 양식을 바꾸면 이 문서와 템플릿 파일을 같은 PR에서 수정한다.

## 머지

기본적으로 `Squash and merge`를 사용한다.

다음 조건을 만족한 후 머지한다.

- CI 성공
- 승인 1명 이상
- 필수 리뷰 해결
- 충돌 없음

머지 후 작업 브랜치는 삭제한다.
