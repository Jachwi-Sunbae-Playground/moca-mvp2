# 문서 정합성 검토

기계가 잡을 수 있는 것과 없는 것을 나누어 검토한다. 아래 순서를 지킨다.

## 1. 기계 검사를 먼저 통과시킨다

```bash
python3 .github/scripts/check_docs.py
```

깨진 링크, 이슈·PR 템플릿 불일치, 목차 누락, 환경변수 불일치는 이 검사가 전부 잡는다. 통과할 때까지 고친 뒤 아래로 넘어간다. 기계가 잡을 것을 눈으로 찾지 않는다.

검사 항목과 각 문서의 정본은 [문서 관리](../../../docs/convention/documentation.md)에 있다.

## 2. 내부 모순을 찾는다

기계가 잡지 못하는 첫 번째 유형이다. 세 가지 패턴을 의심한다.

### 규칙과 예시가 충돌한다

규칙을 정해놓고 같은 문서의 예시가 그 규칙을 어기는 경우다.

> API 컨벤션이 `POST /api/create-property`를 행위 중심 URL이라며 금지한 바로 다음 절에서, kebab-case 예시로 `create-member`를 들고 있었다.

### 같은 값이 문서마다 다르다

> PR 승인 인원이 한 문서는 `최소 한 명`, 다른 문서는 `2명 모두`였다. `409 Conflict`도 한 문서는 사용, 다른 문서는 미사용이었다.

### 새 규칙이 무효화한 옛 규칙이 남아 있다

> `Controller 테스트를 작성하지 않는다`를 정했는데 테스트 종류 표에 `@WebMvcTest` 행이 그대로 있었다.

수정한 문서만 보지 말고, 그 규칙을 언급하는 다른 문서를 함께 확인한다.

## 3. 중복을 찾는다

같은 내용이 두 곳에 있으면 언젠가 한쪽만 낡는다. 발견하면 한 곳으로 모으고 나머지는 링크로 대체한다.

> 백엔드 패키지 트리가 아키텍처 문서와 코드 컨벤션 문서에 각각 그려져 있었다. 한쪽의 패키지 루트 이름이 실제 코드와 달랐는데 아무도 몰랐다.

새 문서를 쓸 때도 이 내용이 이미 어딘가에 있지 않은지 먼저 확인한다.

## 4. 결정 누락을 찾는다

이번 작업에서 정한 것 중 문서에 반영되지 않은 것을 찾는다.

- 대화나 PR에서 정했지만 문서에 옮기지 않은 결정이 있는가
- 코드나 설정을 바꿨는데 관련 문서를 고치지 않았는가
- 컨벤션을 바꿨다면 파급 대상을 모두 고쳤는가
  - `.github/`의 이슈·PR 템플릿
  - `CLAUDE.md`
  - 그 규칙을 참조하는 다른 컨벤션 문서
  - `.github/scripts/check_docs.py`의 검사 항목

> `build.gradle`에 `testAll` 태스크를 추가하고 테스트 컨벤션에는 적었지만, 빌드 명령을 다루는 가이드 문서에는 넣지 않았다.

## 5. 분류 표시를 확인한다

문서를 새로 만들었거나 성격이 바뀌었다면 [문서 관리](../../../docs/convention/documentation.md)의 규칙을 따른다.

- 시점 고정 문서인가 → 머리말에 `문서 성격`과 `갱신 정책`을 적는다
- 파생 문서인가 → 머리말에 `대조 대상`을 적고 `documentation.md`의 파생 문서 표에 등록한다
- 어느 쪽도 확실하지 않으면 표시하지 않는다

## 보고

발견한 것을 유형별로 정리한다. 고친 것과 판단이 필요해 남겨둔 것을 구분한다. 어느 쪽이 맞는지 애매한 모순은 임의로 정하지 말고 묻는다.
