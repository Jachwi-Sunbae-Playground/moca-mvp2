# 테스트 컨벤션

## 원칙

- 테스트 목적에 필요한 범위만 실행하고 테스트 종류를 이름과 애너테이션으로 드러낸다.
- 비즈니스 규칙은 기술 선택과 분리해 순수 단위 테스트로 검증한다.
- JDBC 쿼리와 매핑은 Mock이나 H2가 아니라 Testcontainers MySQL로 검증한다.
- 같은 계약을 여러 계층에서 기계적으로 중복 테스트하지 않는다.

## 테스트 종류

| 종류 | 대상과 방식 |
| --- | --- |
| 단위 테스트 | `new`로 Domain·VO를 생성하고 외부 의존성 없이 규칙을 검증한다 |
| Service 테스트 | 필요한 경우 Stub·Fake로 상태와 결과를 검증한다. 상호작용 자체가 계약일 때만 `verify`를 사용한다 |
| Web 슬라이스 | URL, 직렬화, 입력 검증과 예외 매핑을 격리할 가치가 있을 때 `@WebMvcTest`를 사용한다 |
| JDBC 통합 테스트 | 실제 SQL과 RowMapper를 Testcontainers MySQL에서 검증한다 |
| 인수 테스트 | 핵심 사용자 흐름을 `@SpringBootTest(webEnvironment = RANDOM_PORT)`와 실제 HTTP 요청으로 검증한다 |

## 작성 규칙

- 테스트 본문은 `given-when-then` 순서로 작성한다.
- 테스트 이름은 `메서드명_성공또는실패_조건` 형식을 기본으로 한다.
- 하나의 테스트는 하나의 핵심 행위를 설명한다.
- 시간, 랜덤 값과 외부 시스템은 테스트에서 통제한다.
- 테스트 데이터는 다른 테스트의 실행 순서와 로컬 DB 상태에 의존하지 않는다.
- 실패하는 테스트를 비활성화해 병합하지 않는다.

## 테스트 더블

- Dummy는 사용하지 않는 인자 자리를 채운다.
- Stub은 미리 정한 값을 반환하며 상태 검증에 사용한다.
- Fake는 인메모리 Repository처럼 간소화됐지만 실제로 동작한다.
- Spy·Mock의 호출 검증은 결과만으로 계약을 설명할 수 없을 때 제한적으로 사용한다.
