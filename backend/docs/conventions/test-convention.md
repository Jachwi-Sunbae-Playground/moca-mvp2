# 테스트 컨벤션

## 목적

테스트는 코드 커버리지를 높이는 것이 아니라 변경 이후에도 시스템을 신뢰할 수 있도록 작성한다.

테스트를 선택할 때 `단위 테스트가 더 좋은가, 통합 테스트가 더 좋은가`를 먼저 묻지 않는다.

> 지금 어떤 책임을 검증하고, 어떤 신뢰를 얻고 싶은가?

## 테스트 종류

테스트는 다음 책임을 나누어 검증한다. 종류별 상세 기준은 [테스트 전략](test-strategy.md)을 따른다.

| 종류 | 검증하는 책임 | 실행 방식 |
| --- | --- | --- |
| Domain 단위 테스트 | 비즈니스 규칙 | 순수 Java 객체 |
| Service 단위 테스트 | Use Case의 분기와 협력 | Stub·Mock |
| Repository 슬라이스 테스트 | 실제 SQL과 Row 매핑 | `RepositoryTest` 상속 |
| 통합 테스트 | Bean 연결, 트랜잭션, DB 상태 변화 | `IntegrationTest` 상속 |
| 인수 테스트 | 사용자 관점의 핵심 시나리오 | `AcceptanceTest` 상속 |

기본은 Docker 컨테이너를 사용하는 통합 테스트다. Service 단위 테스트는 [테스트 전략](test-strategy.md)의 `사용하는 경우`에 해당할 때만 예외적으로 작성한다.

## 공통 작성 규칙

- JUnit 5와 AssertJ를 사용한다.
- 테스트 코드는 Given-When-Then 순서로 작성한다.
- private 메서드를 직접 테스트하지 않고 public 행동을 통해 검증한다.
- 별도의 Controller 테스트는 작성하지 않는다. HTTP 레벨 검증은 인수 테스트가 담당한다.
- 테스트가 실패했을 때 어떤 책임이 깨졌는지 알 수 있어야 한다.
- 같은 계약을 여러 계층에서 기계적으로 중복 테스트하지 않는다.
- 하나의 테스트는 하나의 핵심 행위를 설명한다.
- 시간, 랜덤 값과 외부 시스템은 테스트에서 통제한다.
- 테스트 데이터는 다른 테스트의 실행 순서와 로컬 DB 상태에 의존하지 않는다.
- 실패하는 테스트를 비활성화해 병합하지 않는다.

## 테스트 이름

- `@DisplayName`은 기대 행동이 드러나는 한국어 문장으로 작성한다.
- 테스트 메서드명은 간결한 영어 `lowerCamelCase`를 사용한다.

## Assertion

- 실제 결과를 우선 검증한다.
- 예외는 타입뿐 아니라 [Error Code](exception-convention.md)를 함께 검증한다.
- 내부 구현 방식에 대한 `verify()`는 필요한 경우에만 사용한다.

## 테스트 더블

- Dummy는 사용하지 않는 인자 자리를 채운다.
- Stub은 미리 정한 값을 반환하며 상태 검증에 사용한다.
- Fake는 인메모리 Repository처럼 간소화됐지만 실제로 동작한다.
- Spy·Mock의 호출 검증은 결과만으로 계약을 설명할 수 없을 때 제한적으로 사용한다.

## 실행 범위

| 명령 | 범위 |
| --- | --- |
| `./gradlew test` | 인수 테스트를 제외한 전체 |
| `./gradlew testAll` | 인수 테스트를 포함한 전체 |

- CI는 `./gradlew clean build`로 실행하므로 인수 테스트가 제외된다.
- 인수 테스트는 `AcceptanceTest`를 상속하면 `acceptance` 태그를 자동으로 상속받는다. 태그를 개별 테스트에 직접 붙이지 않는다.
