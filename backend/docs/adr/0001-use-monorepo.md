# ADR-0001: 모노레포를 사용한다

- 상태: 승인
- 결정일: 2026-08-04
- 참여자: 자취선배 팀

## 맥락

자취선배는 백엔드, 프론트엔드, 요구사항, 배포 문서, 기술 결정 기록을 함께 변경해야 한다. 초기 팀 프로젝트에서는 저장소 경계를 세분화하는 것보다 모든 팀원이 제품 전체의 변경을 쉽게 발견하고 검토하는 것이 중요하다.

## 결정 기준

- 한 기능의 코드와 문서를 함께 변경하고 검토할 수 있는가
- 저장소와 권한 관리 비용이 팀 규모에 적절한가
- 새로운 팀원이 전체 구조를 빠르게 파악할 수 있는가
- 프론트엔드와 백엔드의 도구가 서로 방해하지 않게 실행 범위를 나눌 수 있는가

## 결정

`backend`, `frontend`, 공통 설정을 하나의 GitHub 저장소에서 관리하는 모노레포를 사용한다. 영역 하나에서만 사용하는 코드, 문서, 환경변수 예시와 로컬 인프라는 해당 영역 안에서 관리한다. 루트에는 저장소 전체가 공유하는 파일만 둔다. CI는 경로 필터를 사용해 필요한 영역만 실행한다.

## 근거

- API 변경과 관련 문서를 하나의 PR에서 함께 검토할 수 있다.
- 팀이 관리해야 할 저장소, 권한, 이슈와 PR 위치가 하나로 줄어든다.
- 초기에는 서비스별 독립 배포보다 빠른 협업과 변경 가시성이 더 중요하다.
- `backend/docs`를 백엔드 코드와 함께 버전 관리하면 Notion 논의와 실제 구현이 어긋나는 위험을 줄일 수 있다.
- 백엔드 전용 Compose, 환경변수 예시와 Java 코드 스타일을 `backend`에 두면 프론트엔드 설정과 이름이 충돌하지 않는다.

## 검토한 대안

| 대안 | 장점 | 단점 | 선택하지 않은 이유 |
| --- | --- | --- | --- |
| 프론트엔드와 백엔드 별도 저장소 | 권한과 배포 주기를 완전히 분리할 수 있다 | 기능 변경이 여러 PR과 저장소에 흩어진다 | 현재 팀 규모에서는 분리 비용이 이점보다 크다 |
| 코드 저장소와 문서 도구만 사용 | 문서 편집과 토론이 편하다 | 구현과 결정 기록의 버전이 어긋날 수 있다 | 최종 합의와 증거는 코드 변경과 함께 남겨야 한다 |

## 결과와 트레이드오프

### 기대하는 결과

- 기능, CI, 문서의 변경 이력을 한곳에서 추적한다.
- 팀원이 제품 전체의 구조와 진행 상황을 쉽게 확인한다.

### 감수하는 비용과 한계

- 저장소가 커지면 CI 시간과 탐색 범위가 증가할 수 있다.
- 공통 설정과 영역 전용 설정의 경계를 팀이 지속해서 구분해야 한다.
- 영역별 권한과 릴리스 주기를 완전히 분리하기 어렵다.

## 검증 방법

- 루트 문서만 보고 각 구성 요소와 문서 위치를 찾을 수 있는지 확인한다.
- 백엔드 변경에서 백엔드 CI만 실행되는지 확인한다.

## 재검토 조건

- 구성 요소별 배포 주기나 접근 권한을 독립적으로 관리해야 한다.
- 경로 필터를 적용해도 CI 시간이 팀의 개발 흐름을 방해한다.
- 저장소 크기 때문에 clone, 탐색, 도구 실행 비용이 유의미하게 증가한다.
