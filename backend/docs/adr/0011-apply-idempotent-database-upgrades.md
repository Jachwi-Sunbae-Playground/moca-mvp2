# ADR-0011: 멱등 SQL로 기존 데이터베이스를 보강한다

- 상태: 승인
- 결정일: 2026-08-25
- 참여자: Moca MVP2
- 문서 성격: 시점 고정(부분)
- 갱신 정책: 맥락·결정·근거·검토한 대안은 고정한다. 결과와 재검토 조건만 갱신한다
- 확장하는 결정: [ADR-0009](0009-use-disposable-database-schema.md)

## 맥락

ADR-0009는 MVP2 개발 중 DB를 폐기할 수 있다는 전제로 현재 스키마 한 벌만 유지했다. 이후 단일 EC2 운영 환경에 실제 매물·사진·체크 기록이 생겼고, Google 회원을 닉네임 인증으로 전환하려면 소유 데이터와 회원 ID를 보존한 채 `nickname_credentials`를 추가해야 한다. Flyway 전체 이력을 복원하는 범위는 이번 작은 전환에 비해 크다.

## 결정

- 새 DB는 계속 `db/init/001-schema.sql`과 `002-seed.sql`로 초기화한다.
- 기존 DB에 필요한 변경은 `db/upgrade/NNN-*.sql`에 번호순, 순방향, 멱등 SQL로 추가한다.
- 애플리케이션 시작 시 upgrade SQL을 번호순으로 실행하고 하나라도 실패하면 시작을 중단한다.
- 배포된 upgrade SQL은 수정하지 않는다.
- 이번 전환은 기존 회원마다 닉네임 자격정보가 없을 때만 추가하고 소유 FK와 기존 행은 변경하지 않는다.
- Flyway는 다시 도입하지 않는다.

## 근거

- 첫 닉네임 인증 릴리스가 이전 버전의 EC2 배포 스크립트로 실행되어도 JAR 자체가 필요한 additive 변경을 적용할 수 있다.
- 반복 시작에 안전한 SQL은 로컬 기존 볼륨과 운영 DB에 같은 절차를 제공한다.
- 기존 회원 ID를 유지하므로 매물·사진·메모·체크리스트 소유 관계를 옮기지 않아도 된다.
- 현재 변경 수와 운영 인스턴스가 하나라 전용 마이그레이션 프레임워크 없이도 검증 범위를 작게 유지할 수 있다.

## 검토한 대안

| 대안 | 장점 | 선택하지 않은 이유 |
| --- | --- | --- |
| 운영 DB를 초기화 | 구현이 가장 단순하다 | 실제 사용자 기록을 잃는다 |
| Flyway 재도입 | 적용 이력과 잠금을 표준화한다 | 기존 baseline 설정과 전체 이력 정리 범위가 커진다 |
| 배포 스크립트에서만 SQL 실행 | 애플리케이션과 DDL을 분리한다 | 첫 전환은 서버에 설치된 이전 스크립트가 실행되어 새 SQL을 알 수 없다 |
| 수동 콘솔 SQL | 구현 변경이 작다 | 누락·순서 오류가 발생하고 환경 재현성이 없다 |

## 결과와 트레이드오프

- 애플리케이션 DB 계정에 현재 additive DDL 권한이 필요하다.
- 실행 이력 테이블이 없으므로 모든 upgrade SQL 자체가 반복 안전해야 한다.
- 다중 인스턴스 동시 시작이나 긴 스키마 변경에는 적합하지 않다.
- 운영 적용 전 백업과 Testcontainers 반복 실행 검증을 유지한다.

## 검증 방법

- 빈 DB가 init SQL만으로 현재 스키마를 만든다.
- 레거시 회원이 있는 DB에 upgrade SQL을 두 번 적용해 회원·소유 데이터와 기존 자격정보가 유지되는지 확인한다.
- 애플리케이션 전체 통합 테스트가 닉네임 생성·공유·보호와 기존 소유자 격리를 검증한다.

## 재검토 조건

- upgrade 파일이 여러 개 누적되어 적용 여부 추적이 필요해진다.
- 테이블 재작성이나 장시간 잠금이 필요한 변경이 생긴다.
- 애플리케이션 인스턴스를 둘 이상 동시에 배포한다.
- DB 계정에서 DDL 권한을 분리해야 한다.
