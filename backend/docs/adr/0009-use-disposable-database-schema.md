# ADR-0009: 폐기 가능한 DB를 단일 스키마로 초기화한다

- 상태: 승인
- 결정일: 2026-08-22
- 참여자: Moca MVP2
- 문서 성격: 시점 고정(부분)
- 갱신 정책: 맥락·결정·근거·검토한 대안은 고정한다. 결과와 재검토 조건만 갱신한다
- 대체하는 결정: [ADR-0007](0007-use-flyway-for-database-migrations.md)

## 맥락

MVP1은 사용자 데이터가 있는 DB를 여러 버전의 코드와 함께 운영하기 위해 Flyway 변경 이력을 사용했다. Moca MVP2는 MVP1 `develop`의 코드와 Git 이력만 가져와 새 개인 환경에서 시작하며, 기존 운영 DB와 사용자 데이터를 이전하지 않는다. 현재 목표는 로컬에서 기능을 빠르게 바꾸고 필요하면 DB를 다시 만드는 것이다.

누적 마이그레이션에는 현재 코드가 사용하지 않는 초기 모델과 중간 변환 단계가 남아 있다. 이 이력을 계속 확장하면 현재 스키마를 이해하고 AI와 함께 수정하는 비용이 커진다.

## 결정

- Flyway 의존성과 `db/migration`을 현재 브랜치에서 제거한다.
- 현재 코드가 실제 사용하는 테이블은 `db/init/001-schema.sql` 하나를 정본으로 관리한다.
- 로컬 확인용 시스템 기본 항목은 `db/init/002-seed.sql`로 분리한다.
- Docker MySQL은 데이터 볼륨이 비어 있을 때 두 파일을 순서대로 실행한다.
- 테스트는 Spring SQL 초기화로 같은 두 파일을 Testcontainers MySQL에 적용한다.
- 애플리케이션의 일반 기동과 운영 프로필에서는 SQL 자동 초기화를 실행하지 않는다.
- 스키마를 바꾸면 단일 스키마를 수정하고 로컬 DB 볼륨을 명시적으로 다시 만든다.
- MVP1 운영 데이터와 DB 변경 이력은 이전하지 않는다. 필요한 과거 SQL은 `mvp1-baseline` 태그에서 확인한다.

## 근거

- 빈 DB에서 현재 구조를 한 번에 읽고 재현할 수 있다.
- 더 이상 사용하지 않는 테이블과 중간 변경 단계를 새 실험에 끌고 가지 않는다.
- 로컬과 테스트가 같은 SQL을 사용해 스키마 차이를 줄인다.
- 운영 데이터 호환이 필요 없는 현재 단계에서는 마이그레이션 도구의 안전성보다 변경 속도와 이해 비용 절감의 가치가 크다.

## 검토한 대안

| 대안 | 장점 | 선택하지 않은 이유 |
| --- | --- | --- |
| Flyway 이력을 그대로 유지 | 기존 DB를 이어서 운영할 수 있다 | MVP1 DB를 이전하지 않으며 현재 실험에 불필요한 과거 구조가 계속 쌓인다 |
| Flyway를 유지하고 새 baseline migration 생성 | 도구 사용법을 유지한다 | 폐기 가능한 단일 개인 환경에서는 버전 관리 비용만 남는다 |
| JPA 자동 DDL 사용 | 엔티티에서 빠르게 테이블을 만든다 | Spring JDBC 쿼리와 DB 제약을 정본으로 표현하기 어렵다 |

## 결과와 트레이드오프

- 스키마 변경은 단순해지지만 기존 데이터가 있는 DB를 자동 변환하지 못한다.
- DB 초기화는 데이터 삭제를 전제로 하므로 개발자가 명시적으로 실행해야 한다.
- 실제 사용자 데이터를 보존해야 하는 시점부터는 단일 스키마 수정만으로 배포할 수 없다.
- 현재 스키마와 기본 데이터 적용은 통합 테스트로 검증한다.

## 검증 방법

- 빈 MySQL 8.4 컨테이너에 스키마와 기본 데이터를 적용한다.
- 백엔드 전체 테스트에서 현재 12개 테이블과 시스템 기본 항목 수를 확인한다.
- 로컬 Compose를 새 볼륨으로 시작해 애플리케이션이 조회·저장할 수 있는지 확인한다.

## 재검토 조건

- 보존해야 하는 실제 사용자 데이터가 생긴다.
- 서로 다른 애플리케이션 버전이 하나의 DB를 순차 배포한다.
- 데이터 변환, 무중단 DDL 또는 장애 복구용 변경 이력이 필요해진다.
