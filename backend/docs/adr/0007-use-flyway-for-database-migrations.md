# ADR-0007: Flyway로 데이터베이스 변경 이력을 관리한다

- 상태: 승인
- 결정일: 2026-08-12
- 참여자: 자취선배 백엔드 팀
- 문서 성격: 시점 고정(부분)
- 갱신 정책: 맥락·결정·근거·검토한 대안은 고정한다. 결과와 재검토 조건만 갱신한다

## 맥락

v1.0은 Spring Boot SQL 초기화가 하나의 `schema.sql`을 매번 실행하는 방식이었다. 이 방식은 빈 로컬 DB를 만드는 데는 충분했지만 이미 회원·매물·체크리스트·방문 데이터가 있는 DB에 v1.1 스키마를 순서대로 적용하고, 적용 여부와 스크립트 변경을 추적할 수 없다. v1.1은 기존 12개 테이블과 데이터를 보존하면서 사전 메모 테이블, 사용자 작성 체크 항목, 방문 인라인 메모를 위한 컬럼과 제약을 확장해야 한다.

MySQL DDL은 문장 단위로 암시적 커밋될 수 있다. 따라서 실패한 변경을 애플리케이션 재시작만으로 원복할 수 있다고 가정하지 않고, 적용 전 백업과 별도 DB 복구 리허설이 필요하다.

## 결정

- 데이터베이스 변경 이력은 Flyway 13.0.0과 MySQL 전용 모듈로 관리한다.
- Spring Boot SQL 초기화는 비활성화하고 `classpath:db/migration`의 버전 마이그레이션만 사용한다.
- v1.0의 전체 스키마와 기준 데이터는 `V1__create_v1_0_schema.sql`로 보존한다. 적용된 버전 파일은 수정·삭제·이름 변경하지 않는다.
- v1.1 전환은 구조 확장, 데이터 backfill, 제약 확정을 서로 다른 순방향 마이그레이션으로 나눈다.
- 빈 DB는 V1부터 최신 버전까지 자동 적용한다.
- 기존 pre-Flyway v1.0 DB는 백업·복구 리허설과 스키마 확인 뒤 운영자가 버전 1을 명시적으로 baseline하고 최신 버전까지 적용한다.
- `baseline-on-migrate`는 기본값을 `false`로 유지한다. 기존 v1.0 DB를 승인된 절차로 전환하는 한 번의 실행에서만 `target=1`과 함께 사용한다.
- 시작할 때 checksum 검증이나 마이그레이션이 실패하면 애플리케이션 기동도 실패하게 한다.
- 운영 DB에 자동 down migration이나 `clean`을 제공하지 않는다. 실패하면 데이터 유입 시점에 따라 백업 복구 또는 후속 순방향 마이그레이션을 선택한다.

## 근거

- 버전, 적용 순서, checksum과 성공 여부를 `flyway_schema_history`에서 일관되게 확인할 수 있다.
- 빈 DB와 기존 v1.0 DB가 같은 V2 이후 변경 이력을 공유한다.
- 명시적 baseline은 임의의 비어 있지 않은 DB를 v1.0으로 오인해 승인하는 위험을 기본 설정에서 차단한다.
- 확장과 backfill을 분리하면 실패 지점과 데이터 검증 범위가 드러난다.
- 순방향 추가 마이그레이션은 이미 기록된 이력을 바꾸지 않고 운영 장애를 수정할 수 있다.

## 검토한 대안

| 대안 | 장점 | 우려 | 선택하지 않은 이유 |
| --- | --- | --- | --- |
| `schema.sql` 유지 | 도구와 설정이 단순하다 | 적용 버전·순서·checksum을 추적하지 못하고 운영 데이터 backfill 경계가 없다 | 기존 DB를 안전하게 v1.1로 전환할 수 없다 |
| Liquibase | 구조화된 changelog와 rollback 기능이 풍부하다 | 현재 팀의 SQL 중심 스키마와 비교해 학습·설정 비용이 크다 | 이번 변경은 명시적인 MySQL SQL과 순방향 복구로 충분하다 |
| 배포 때 수동 SQL 실행 | 실행 시점을 운영자가 완전히 통제한다 | 실행 이력과 애플리케이션 버전이 분리되고 누락·중복 적용 위험이 있다 | 자동 검증과 빈 DB 재현성을 잃는다 |
| `baseline-on-migrate=true` 상시 설정 | 기존 DB 전환 절차가 짧다 | 정체를 확인하지 않은 비어 있지 않은 DB도 현재 버전으로 승인할 수 있다 | 안전하지 않은 기본값이다 |
| 자동 down migration | 빠르게 이전 구조로 돌아갈 수 있다 | 새로 유입된 데이터와 비가역 DDL을 안전하게 되돌리기 어렵다 | 복구 가능성을 과장하고 데이터 손실 위험을 높인다 |

## 결과와 트레이드오프

### 기대하는 결과

- 빈 DB는 한 번의 애플리케이션 기동으로 최신 스키마와 기준 데이터를 얻는다.
- 기존 v1.0 DB는 안정적인 ID와 관계, 질문 스냅샷, 상태 버전을 유지한 채 v1.1 구조로 전환된다.
- 이미 적용된 SQL이 바뀌거나 순서가 어긋나면 배포 전에 실패한다.
- 새 변경은 다음 버전 파일로만 추가돼 코드 리뷰와 장애 분석에서 이력을 재현할 수 있다.

### 감수하는 비용과 한계

- 기존 DB 최초 전환에는 백업·복구 리허설·명시적 baseline 절차가 추가된다.
- MySQL DDL의 암시적 커밋 때문에 마이그레이션 전체가 하나의 트랜잭션으로 원복되지 않는다.
- 운영 데이터가 들어온 뒤 단순 DB 복구를 선택하면 백업 이후 데이터가 사라질 수 있다.
- v1.1 제거 대상 컬럼과 프리셋 데이터는 이번 expand/backfill 단계에서 삭제하지 않아 정리 작업이 남는다.

## 검증 방법

- Testcontainers MySQL 8.4의 빈 DB에 전체 마이그레이션을 적용하고 재실행 시 추가 적용이 없음을 검증한다.
- 실제 V1 스크립트로 만든 pre-Flyway DB에 회원·매물·사진·체크리스트·방문 데이터를 넣고 명시적 baseline 뒤 행·ID·관계·스냅샷·버전 보존을 검증한다.
- backfill 값, 사용자 작성 항목 제약, 인라인 메모 길이·개행·버전 제약과 GOSHIWON 비활성화를 실제 MySQL에서 검증한다.
- 적용된 checksum을 변조했을 때 검증과 기동이 실패하는지 확인한다.

## 재검토 조건

- 무중단 배포에서 장시간 DDL과 온라인 스키마 변경 도구가 필요해진다.
- 여러 서비스가 한 스키마를 독립적으로 변경한다.
- 테넌트별 스키마나 여러 데이터베이스에 같은 변경을 조율해야 한다.
- 복구 목표가 백업 복원보다 짧아 자동화된 시점 복구나 별도 rollback 체계가 필요하다.
