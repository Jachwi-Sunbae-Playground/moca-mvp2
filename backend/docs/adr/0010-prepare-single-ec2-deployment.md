# ADR-0010: 단일 EC2 최소 배포를 준비한다

- 상태: 승인
- 결정일: 2026-08-22
- 참여자: Moca MVP2
- 문서 성격: 시점 고정(부분)
- 갱신 정책: 맥락·결정·근거·검토한 대안은 고정한다. 결과와 재검토 조건만 갱신한다
- 대체하는 결정: [ADR-0008](0008-deploy-with-aws-native-pipeline.md)

## 맥락

MVP1 배포는 우테코 계정의 IAM·네트워크 제약 아래 ALB, WAF, RDS, S3, CloudFront, CodePipeline과 CodeDeploy를 사용했다. MVP2는 개인 AWS 계정에서 외부 사용자가 기능을 볼 수 있는 환경 하나만 필요하다. 기능 개발이 끝날 때까지 배포하지 않고 로컬 개발에 집중하며, 첫 배포의 구성 시간과 반복 배포 시간을 최소화한다.

## 결정

- 운영 환경은 하나만 두고 단일 EC2에서 Caddy, 프론트엔드 정적 파일, Spring Boot와 MySQL을 실행한다.
- Caddy가 HTTPS와 SPA 서빙을 담당하고 `/api` 요청만 `127.0.0.1:8080`으로 전달한다.
- MySQL 데이터는 EC2의 별도 영속 볼륨에 두고 외부 3306 포트를 열지 않는다.
- 사진 원본은 EC2 디스크가 아니라 비공개 S3 버킷에 둔다.
- 배포는 GitHub Actions의 수동 실행만 허용한다. AWS 인증은 장기 Access Key 대신 GitHub OIDC를 사용한다.
- Actions는 릴리스 파일을 S3에 올리고 SSM Run Command로 EC2 배포 스크립트를 실행한다.
- PR CI와 배포를 분리한다. 배포 워크플로에서는 이미 확인한 테스트를 반복하지 않는다.
- MVP2 기능 개발이 끝나기 전에는 AWS 리소스를 생성하거나 워크플로를 실행하지 않는다.

## 근거

- 한 인스턴스와 한 환경은 구성 요소와 월 고정비를 줄인다.
- Caddy가 인증서 발급·갱신과 같은 도메인 서빙을 단순화한다.
- S3 사진 저장은 인스턴스 교체와 사진 수명 주기를 분리한다.
- OIDC와 SSM은 SSH 포트 및 장기 AWS 키 없이 배포할 수 있다.
- 수동 실행은 로컬 개발 단계의 실수 배포를 막으면서 필요할 때 반복 배포 시간을 짧게 유지한다.

## 검토한 대안

| 대안 | 장점 | 선택하지 않은 이유 |
| --- | --- | --- |
| 기존 AWS 네이티브 구성 유지 | 검증된 격리와 관리형 서비스 | 개인 MVP에 구성 요소와 비용이 과하다 |
| ECS/Fargate | 컨테이너 배포와 교체가 편하다 | 첫 설정 범위와 운영 요소가 늘어난다 |
| RDS 사용 | 백업과 장애 대응이 편하다 | MVP2 첫 공개 단계의 최소 비용 목표보다 비싸다 |
| SSH 기반 Actions | 구현이 단순하다 | 공개 SSH 포트와 배포용 개인키 관리가 필요하다 |
| `main` 자동 배포 | 병합 직후 반영된다 | 로컬 우선 단계에서 원치 않는 배포가 발생할 수 있다 |

## 결과와 트레이드오프

- EC2 한 대가 장애 지점이며 애플리케이션과 DB가 자원을 경쟁한다.
- 무중단 배포를 보장하지 않고 짧은 재시작을 허용한다.
- MySQL 백업, 디스크 용량과 메모리를 직접 관리해야 한다.
- 실제 부하나 데이터 가치가 커지면 RDS, 다중 인스턴스와 별도 정적 호스팅으로 분리한다.

## 검증 방법

- 배포 파일은 로컬 구문 검사와 프론트엔드·백엔드 빌드를 통과해야 한다.
- 첫 배포 때 HTTPS, SPA 새로고침, `/api/actuator/health`, 로그인 callback과 S3 사진 흐름을 확인한다.
- 직전 릴리스 전환과 DB 백업 복구를 별도 리허설한다.

## 재검토 조건

- 외부 사용자의 지속 사용으로 가용성 요구가 생긴다.
- DB 데이터 손실 허용 범위가 일일 백업보다 짧아진다.
- CPU·메모리·디스크 병목이 한 인스턴스에서 반복된다.
- 자동 배포나 무중단 배포가 개발 속도에 더 유리해진다.
