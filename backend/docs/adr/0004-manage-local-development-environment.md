# ADR-0004: 재현 가능한 개발 환경을 관리한다

- 상태: 승인
- 결정일: 2026-08-04
- 참여자: 자취선배 백엔드 팀
- 문서 성격: 시점 고정(부분)
- 갱신 정책: 맥락·결정·근거·검토한 대안은 고정한다. 결과와 재검토 조건만 갱신한다

## 맥락

팀원마다 Java, Gradle과 MySQL 설치 상태가 다르면 실행 실패를 재현하기 어렵다. 개발 환경은 특정 팀원의 로컬 설정이 아니라 저장소의 파일과 명령으로 재현되어야 한다.

## 결정

- Gradle `8.14.3` Wrapper로 빌드 도구 버전을 고정한다.
- 로컬 MySQL은 `backend/compose.yaml`의 Docker Compose로 실행한다.
- 로컬 설정 예시는 `backend/.env.example`, 개인 값은 Git에서 제외되는 `backend/.env`에 둔다.
- 테스트는 H2 대신 Testcontainers의 MySQL `8.4.10`을 사용한다.
- 공통 `IntegrationTest`가 `@ServiceConnection`으로 임시 DB 연결 정보를 주입한다.
- GitHub Actions는 Java 21과 Gradle Wrapper로 `./gradlew clean build --no-daemon`을 실행한다.
- 백엔드 전용 환경과 도구 설정은 `backend` 안에 두고 저장소 전체가 공유하는 파일만 루트에 둔다.

## 근거

- Wrapper와 Docker 이미지 버전 고정은 팀원의 사전 설치 상태 차이를 줄인다.
- Compose 파일과 환경변수 예시를 백엔드에 두면 프론트엔드 환경과 경계가 분명해진다.
- Testcontainers는 실제 MySQL SQL과 매핑을 격리된 환경에서 검증한다.
- GitHub Actions는 로컬 성공이 다른 환경에서도 재현되는지 PR마다 확인한다.

## 검토한 대안

| 대안 | 장점 | 우려 | 선택하지 않은 이유 |
| --- | --- | --- | --- |
| MySQL 직접 설치 | 컨테이너 실행 비용이 없다 | 버전, 계정, 문자셋과 기존 데이터가 달라진다 | 팀 환경을 동일하게 재현하기 어렵다 |
| 루트 Compose와 `.env.example` | 루트에서 전체 서비스를 실행하기 쉽다 | 현재는 백엔드에서만 사용해 소유 경계가 흐려진다 | 공통 실행 필요가 생길 때 별도 루트 구성을 추가한다 |
| Repository Mock 중심 테스트 | 빠르고 실패 범위가 작다 | 실제 SQL과 매핑 오류를 발견하지 못한다 | 데이터 접근 검증을 대체할 수 없다 |
| 로컬 빌드만 확인 | 구성이 단순하다 | 누락과 환경 차이를 자동으로 발견하지 못한다 | 팀 소유 환경의 완료 기준을 충족하기 어렵다 |

## 결과와 트레이드오프

### 기대하는 결과

- 새 팀원이 백엔드 디렉터리의 문서와 명령만으로 환경을 재현한다.
- 로컬과 CI가 같은 Java, Gradle과 MySQL 기준으로 검증한다.
- 백엔드와 프론트엔드가 각자의 환경 설정을 독립적으로 관리한다.

### 감수하는 비용과 한계

- 개발과 통합 테스트에 Docker가 필요하다.
- 최초 이미지 다운로드와 컨테이너 시작 때문에 테스트가 느려질 수 있다.
- Compose는 `.env`를 자동으로 읽지만 Spring 프로세스에는 환경변수를 별도로 전달해야 한다.
- 프론트엔드까지 한 번에 실행하는 공통 Compose는 아직 없다.

## 검증 방법

- `backend`에서 `docker compose up -d mysql` 후 MySQL이 `healthy`인지 확인한다.
- Compose MySQL 없이 Docker만 실행한 상태에서 `./gradlew test`가 성공하는지 확인한다.
- PR의 Backend CI가 전체 빌드와 Testcontainers 테스트를 통과하는지 확인한다.

## 재검토 조건

- 프론트엔드와 백엔드를 한 명령으로 실행할 필요가 생긴다.
- Docker 사용이 제한되거나 테스트 시간이 개발 흐름을 방해한다.
- 개발·운영 환경 분리 또는 비밀 관리 방식이 필요해진다.
