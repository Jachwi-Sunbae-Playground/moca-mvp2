# ADR-0006: 비공개 S3 호환 저장소에 매물 사진을 저장한다

- 상태: 승인
- 결정일: 2026-08-10
- 참여자: 자취선배 백엔드 팀
- 문서 성격: 시점 고정(부분)
- 갱신 정책: 맥락·결정·근거·검토한 대안은 고정한다. 결과와 재검토 조건만 갱신한다

## 맥락

매물 사진은 회원의 생활 공간 후보와 연결된 민감한 기록이다. 사진 바이너리는 MySQL 트랜잭션과 다른 외부 저장소에 보관해야 하며, 소유권 검증 없는 공개 URL이나 내부 객체 키 노출을 허용할 수 없다. 동시에 1차 MVP는 비동기 삭제 큐, Outbox와 재시도 워커 없이 업로드·삭제 실패를 명확하게 응답해야 한다.

## 결정

- 사진 바이너리는 공개 ACL을 사용하지 않는 S3 호환 객체 저장소에 보관한다.
- MySQL에는 매물·회원 소유권, 내부 `storageKey`, MIME, 크기, SHA-256과 생성 시각만 저장한다.
- 저장 키는 원본 파일명 대신 `members/{memberId}/properties/{propertyId}/{uuid}` 형식으로 서버가 생성한다.
- `PhotoStorage` 인터페이스가 `upload`, `open`, `deleteIfExists` 경계를 제공하고 `S3CompatiblePhotoStorage`가 S3 SDK로 구현한다.
- 사진 본문은 Presigned URL이나 redirect를 제공하지 않고 JWT와 매물·사진 소유권을 확인한 백엔드 API가 스트리밍한다.
- 외부 저장소 호출은 DB 트랜잭션 밖에서 수행한다. 업로드 뒤 DB 저장이 실패하면 해당 객체를 동기 보상 삭제한다.
- 사진과 매물 삭제는 외부 객체가 삭제되거나 이미 없음을 확인한 뒤 DB 메타데이터를 삭제한다.
- 로컬 S3 호환 저장소는 Docker Compose의 MinIO로 실행하고 자동 테스트는 `PhotoStorage` 계약을 만족하는 Fake를 사용한다.

## 근거

- 객체 저장소는 이미지 바이너리의 용량 증가를 관계형 DB와 분리하고 S3 호환 배포 환경을 선택할 수 있게 한다.
- 비공개 bucket과 인증 백엔드 스트리밍은 저장소 URL을 아는 것만으로 사진에 접근하는 경로를 차단한다.
- 서버 생성 UUID 키는 원본 파일명의 개인정보·경로 문자열과 이름 충돌을 저장소 경계에서 제거한다.
- 짧은 DB 트랜잭션과 동기 보상은 외부 네트워크 호출 때문에 매물 행 잠금이 길어지는 것을 피하면서 MVP 실패 경계를 설명할 수 있게 한다.
- MinIO는 실제 운영 자격증명 없이 같은 S3 API 경계를 로컬에서 재현한다.

## 검토한 대안

| 대안 | 장점 | 우려 | 선택하지 않은 이유 |
| --- | --- | --- | --- |
| MySQL BLOB | DB 트랜잭션 하나로 메타데이터와 바이너리를 저장한다 | DB 용량·백업·쿼리 I/O가 사진과 함께 커진다 | 제품 데이터 조회와 파일 전송의 부하를 분리하기 어렵다 |
| 서버 로컬 파일 시스템 | 구현과 로컬 실행이 단순하다 | 다중 인스턴스·컨테이너 교체·배포 환경에서 파일이 공유되지 않는다 | 운영 저장소로 확장할 수 있는 일관된 경계가 아니다 |
| 공개 객체 URL | 백엔드 스트리밍 부하가 없다 | URL 유출·추측만으로 민감한 사진을 조회할 수 있다 | 사용자 자원 소유권 정책을 우회한다 |
| Presigned URL | 공개 ACL 없이 클라이언트가 객체 저장소에서 직접 읽는다 | URL 유효기간·발급 정책과 클라이언트 저장소 의존이 추가된다 | 1차 MVP의 인증 스트리밍 계약에 포함되지 않는다 |
| 비동기 삭제 큐·Outbox | 실패 재시도와 최종 일관성을 자동화한다 | 테이블·워커·운영 정책이 추가된다 | 현재 후속 TODO이며 MVP 범위를 넘는다 |

## 결과와 트레이드오프

### 기대하는 결과

- 사진 접근은 모든 경로에서 JWT 회원과 매물 소유권 검증을 거친다.
- DB에는 파일 바이너리와 원본 파일명이 남지 않는다.
- 운영 S3 호환 저장소와 로컬 MinIO가 같은 애플리케이션 경계를 사용한다.
- 업로드·삭제의 부분 실패가 계약된 오류와 보상 흐름으로 드러난다.

### 감수하는 비용과 한계

- 백엔드가 원본 사진 스트리밍 대역폭과 연결 수를 부담한다.
- 외부 객체 저장소와 DB를 하나의 원자적 트랜잭션으로 묶지 못한다.
- 보상 삭제까지 실패하면 구조화 로그를 확인해 객체를 수동 정리해야 한다.
- 일부 매물 사진 삭제 뒤 후속 객체 삭제가 실패하면 DB 메타데이터가 일시적으로 없는 객체를 가리킬 수 있다.
- 현재는 이미지 가공, CDN, Presigned URL과 자동 재시도 작업이 없다.

## 검증 방법

- JPEG·PNG·WebP의 MIME·시그니처·실제 디코딩을 자동 테스트한다.
- Fake 저장소로 업로드·본문·삭제와 외부 실패·보상 실패 결과를 검증한다.
- Testcontainers MySQL에서 사진 소유권 FK, MIME·크기 CHECK, 저장 키 UNIQUE와 정렬 인덱스를 검증한다.
- 로컬 MinIO bucket 초기화, 애플리케이션 기동과 사진 OpenAPI 계약을 확인한다.

## 재검토 조건

- 사진 조회 트래픽이 백엔드 대역폭이나 지연 목표를 위협한다.
- CDN이나 Presigned URL을 사용하면서도 현재 소유권·만료 정책을 유지할 수 있다.
- 보상·삭제 실패가 반복돼 비동기 작업 큐와 자동 재시도가 필요하다.
- 운영 객체 저장소가 S3 호환 API를 제공하지 않는다.
- 이미지 리사이징·EXIF 제거·악성 파일 검사 요구가 추가된다.
