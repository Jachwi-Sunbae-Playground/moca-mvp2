# ADR-0003: 데이터베이스와 영속성 방식을 선택한다

- 상태: 승인
- 결정일: 2026-08-04
- 참여자: 자취선배 백엔드 팀

## 맥락

초기 MVP는 빠르게 사용자 가설을 검증해야 하며 복잡한 연관관계와 도메인 규칙은 아직 충분히 드러나지 않았다. 현재 필요한 것은 팀원이 동일한 데이터베이스에서 실제 SQL 동작을 명확하게 확인하는 것이다.

## 결정

- 데이터베이스는 MySQL `8.4.10`을 사용한다.
- 데이터 접근은 Spring JDBC의 `JdbcTemplate`을 사용한다.
- 최상위 패키지는 업무 도메인별로 나누고 각 도메인 안에서 `controller`, `service`, `repository`, `domain`, `dto` 레이어를 사용한다.
- 의존 방향은 `controller → service → repository`를 기본으로 한다.
- JPA와 헥사고날 아키텍처는 1차 MVP에서 사용하지 않는다.
- API DTO와 서비스의 Command/Result는 경계를 분리할 필요가 있을 때 사용하며 모양이 같은 DTO를 기계적으로 복제하지 않는다.

## 근거

- MySQL 버전을 고정하면 개발과 테스트의 SQL 차이를 줄일 수 있다.
- `JdbcTemplate`은 실행 SQL과 매핑을 명시적으로 확인할 수 있다.
- 현재 복잡도에서는 단순한 레이어드 구조가 팀의 공통 이해와 구현 속도에 유리하다.
- HTTP DTO와 서비스 입출력 경계를 유지하면 이후 구조 변경 지점을 남길 수 있다.

## 검토한 대안

| 대안 | 장점 | 우려 | 선택하지 않은 이유 |
| --- | --- | --- | --- |
| JPA | 객체 중심 상태 변경과 연관관계 매핑, 반복 SQL 감소 | 숨은 쿼리, N+1, 영속성 컨텍스트 학습 비용 | 현재 모델 복잡도에서 이점이 확인되지 않았다 |
| 처음부터 헥사고날 아키텍처 | 외부 기술과 핵심 로직의 의존 방향을 강하게 통제한다 | 포트, 어댑터와 변환 객체가 증가한다 | MVP 규모보다 구조 비용이 크다 |
| H2 | 실행이 빠르고 설정이 단순하다 | MySQL과 문법, 함수, 제약조건 동작이 다르다 | 실제 JDBC SQL 검증 신뢰도가 낮다 |
| 공유 개발 DB | 팀원이 DB를 직접 실행하지 않아도 된다 | 네트워크와 공유 상태에 의존한다 | 격리와 재현이 어렵다 |

## 결과와 트레이드오프

### 기대하는 결과

- SQL과 데이터 접근 동작을 명시적으로 확인한다.
- 팀원이 코드 위치와 의존 방향을 빠르게 이해한다.
- 실제 복잡도가 드러난 뒤 필요한 구조만 도입한다.

### 감수하는 비용과 한계

- SQL, RowMapper, 키 생성과 조회 코드를 직접 작성해야 한다.
- 복잡한 관계와 상태 전이가 늘면 Service와 Repository가 비대해질 수 있다.
- JPA 또는 헥사고날 구조 전환 시 패키지 이동과 인터페이스 추출이 필요하다.
- 데이터베이스 스키마 마이그레이션 도구는 아직 결정하지 않았다.

## 검증 방법

- Repository 통합 테스트를 실제 MySQL에서 실행한다.
- 코드 리뷰에서 레이어 의존 방향과 불필요한 DTO 복제를 확인한다.
- 반복 SQL, 매핑 중복과 도메인 테스트 어려움을 회고에 기록한다.

## 재검토 조건

- 연관관계와 조회 조합이 복잡해져 수동 매핑 비용이 반복된다.
- 엔티티 생명주기와 상태 전이 규칙이 핵심 복잡도가 된다.
- 외부 시스템 교체나 독립적인 도메인 테스트를 위해 포트 분리가 필요하다.
- 운영 데이터베이스가 MySQL이 아닌 제품으로 결정된다.
