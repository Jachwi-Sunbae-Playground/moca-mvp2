# ADR-0008: 액세스 키 없이 AWS 네이티브 파이프라인으로 배포한다

- 상태: 승인
- 결정일: 2026-08-15
- 참여자: 자취선배 팀
- 문서 성격: 시점 고정(부분)
- 갱신 정책: 맥락·결정·근거·검토한 대안은 고정한다. 결과와 재검토 조건만 갱신한다

## 맥락

1차 MVP v1.1 코드는 저장소에 있었으나 어디에도 배포되어 있지 않았다. 배포 담당자가 로컬에서 빌드해 EC2에 올리는 방식은 배포 지식이 한 사람에게 묶이고, 빌드 결과가 사람마다 달라지며, 배포 성공 여부를 사람이 판단해야 한다.

우테코가 제공한 AWS 계정에는 이 결정을 좌우하는 제약이 있다.

- **IAM Role과 액세스 키를 만들 수 없다.** 제공된 service role(`codepipeline-project`, `codedeploy-project`, `codebuild-project`)과 EC2 인스턴스 role(`ec2-project`)만 쓸 수 있다.
- **VPC·서브넷·보안 그룹·S3 버킷을 여러 팀이 공유한다.** 규칙을 바꾸면 다른 팀에 영향이 간다.
- **삭제 권한이 대부분 없다.** 잘못 만든 리소스를 되돌릴 수 없다.
- **예산 한도가 있다.** 8월 $50, 9월 $60, 10월 이후 $70이며 초과하면 리소스를 종료·삭제한다.
- **모든 리소스에 태그 3종이 필요하다.** 없으면 종료·삭제 대상이 된다.

첫 번째 제약이 결정적이다. GitHub Actions가 액세스 키로 AWS에 배포하는 흔한 방식을 쓸 수 없다.

## 결정

- 배포는 **CodePipeline + CodeDeploy**로 구성한다. 모든 단계가 제공된 service role로 동작하며 액세스 키를 만들지 않는다.
- 빌드는 **CodePipeline `Commands` 액션**으로 수행한다. 별도 CodeBuild 프로젝트를 두지 않는다.
- **배포 빌드는 테스트를 실행하지 않는다.** PR 검증은 GitHub Actions가, 배포 산출물 생성은 CodePipeline이 맡는다.
- 백엔드는 EC2 단일 인스턴스에 배포하고 **systemd로 프로세스를 관리**한다. 프로세스 교체는 `ApplicationStart`의 `systemctl restart`가 보장한다.
- 배포 성공 판정은 `ValidateService` 훅이 `/actuator/health`가 `UP`인지 확인해 내린다. 실패하면 배포를 중단하고 **CodePipeline 스테이지 롤백**으로 직전 정상 실행으로 되돌린다. CodeDeploy 배포 그룹 자체의 롤백은 켜지 않는다.
- 운영 값은 **EC2의 `/etc/jachwi-sunbae/app.env`**(`0600`, 소유자 `root:root`)에 둔다. systemd가 `EnvironmentFile`로 root 권한에서 읽은 뒤 애플리케이션 계정으로 내려간다. 이 파일은 배포 산출물에 포함하지 않는다.
- **애플리케이션은 8080이 아니라 80을 듣는다.** 비루트 계정이 바인딩하도록 systemd 유닛에 `AmbientCapabilities=CAP_NET_BIND_SERVICE`를 준다.
- 프론트엔드는 **S3 + CloudFront**로 서빙하고 백엔드와 **별도 파이프라인**을 둔다.
- 프론트엔드 운영 빌드는 파일명에 **`contenthash`** 를 붙이고, 배포마다 이름이 고정인 `index.html`만 CDN에서 무효화한다.
- 빌드 환경의 런타임 버전을 신뢰하지 않는다. 백엔드는 Corretto 21을, 프론트엔드는 `.nvmrc`의 Node 버전을 **명시적으로 설치해 절대 경로로 실행**한다.
- apex 도메인(`jachwi-sunbae.kr`)은 서비스하지 않는다. `www` 서브도메인만 쓴다.
- 빌드 정의가 콘솔에 있으므로, 파이프라인 설정을 바꾸면 [배포](../operations/deployment.md)와 [프론트엔드 배포](../../../frontend/docs/deployment.md)를 같은 작업에서 고친다.

구성 값과 리소스 식별자는 [배포 아키텍처 설계](../../../docs/operations/deployment-architecture.md)에 있다.

## 근거

- 제공된 service role만으로 동작하므로 **만들 수 없는 자격증명에 의존하지 않는다.** 장기 액세스 키를 어디에도 두지 않는다.
- `Commands` 액션은 파이프라인 서비스 role을 그대로 쓴다. CodeBuild 프로젝트는 파이프라인의 `SourceArtifact`를 읽을 권한이 없어 빌드 입력을 내려받지 못한다.
- 테스트를 한 곳에서만 실행하면 중복이 사라지고 배포 시간이 줄어든다. 통합 테스트가 Testcontainers로 Docker를 요구해 관리형 빌드 환경에 특권 모드가 필요해지는 문제도 피한다. GitHub Actions가 PR과 `main` push 양쪽에서 실행하므로 배포되는 커밋은 이미 검증을 통과한 상태다.
- `systemctl start`는 이미 `active`인 서비스에 아무 일도 하지 않는다. `restart`를 쓰면 이전 상태와 무관하게 프로세스가 교체된다. `ApplicationStop`은 **직전 리비전의 스크립트**로 실행되므로 첫 배포에는 동작하지 않고 직전 리비전이 잘못돼 있으면 동작하지도 않는다. 교체를 이 훅에 기댈 수 없다.
- health 확인을 배포의 마지막 단계로 두면 기동하지 못하는 리비전이 성공으로 기록되지 않는다.
- 환경변수 파일을 CodeDeploy가 덮어쓰는 경로 밖에 두면 배포마다 값이 사라지지 않고, 비밀을 저장소에 커밋하지 않아도 된다. systemd가 root로 읽으므로 애플리케이션 계정에 읽기 권한을 주지 않아도 된다.
- `project-app` 보안 그룹은 `project-lb`에서 오는 80·443만 허용한다. 이 그룹은 공용이므로 8080 규칙을 추가하면 다른 팀 인스턴스에도 열린다. 우리 편의를 위해 남의 노출 범위를 넓히지 않는다.
- `contenthash`는 내용이 바뀌면 파일명이 바뀌므로 브라우저가 옛 파일을 쓸 수 없다. 전체 무효화 방식은 요청을 **빠뜨렸을 때 그 사실이 드러나지 않는다.** 사용자는 옛 파일을 계속 쓰는데 아무도 모른다.
- 관리형 빌드 환경의 기본 런타임 버전은 이미지마다 다르다. 실제로 Node 18이 PATH에서 앞서 `@babel/core` 8을 불러오지 못했다. 버전을 명시하면 어디서 빌드하든 같은 결과가 나온다.

## 검토한 대안

| 대안 | 장점 | 우려 | 선택하지 않은 이유 |
| --- | --- | --- | --- |
| GitHub Actions에서 AWS로 직접 배포 | 워크플로가 저장소에 있어 이력이 남는다 | 액세스 키가 필요하고 OIDC는 IAM 초기 설정 권한이 필요하다 | 둘 다 만들 수 없다 |
| CodeBuild 프로젝트를 파이프라인에 연결 | 빌드 정의를 `buildspec.yml`로 저장소에 둘 수 있다 | `codebuild-project` role에 파이프라인 `SourceArtifact`를 읽을 `s3:GetObject` 권한이 없다 | 빌드 입력을 내려받지 못한다. role 정책을 바꿀 수 없다 |
| 서비스 EC2에서 직접 빌드 | 별도 빌드 환경이 필요 없다 | 서비스 서버의 자원을 쓰고 빌드와 실행 책임이 한 서버에 섞인다 | 배포 시간이 서비스 서버 상태에 영향을 받는다 |
| SSM Parameter Store SecureString | 값 변경 이력이 남고 인스턴스를 다시 만들어도 비밀이 살아남는다 | 인스턴스 role로 동작하지만 **계정 전체가 한 범위**다. `describe-parameters`에 다른 팀 파라미터가 그대로 보인다 | 팀 간 격리가 없어 우리 비밀을 다른 팀 인스턴스가 읽을 수 있다 |
| AWS Secrets Manager | 자동 로테이션을 제공한다 | 시크릿당 월 요금이 붙는다 | 예산 한도에 부담이 된다 |
| 공용 보안 그룹에 8080 규칙 추가 | 애플리케이션 포트를 로컬과 같게 유지한다 | 같은 그룹을 쓰는 다른 팀 인스턴스에도 8080이 열린다 | 우리 편의를 위해 남의 노출 범위를 넓히는 변경이다 |
| EC2 안에서 iptables로 80 → 8080 포워딩 | 애플리케이션을 고치지 않아도 된다 | 규칙이 저장소에 남지 않고 재부팅 시 사라져 따로 영속화해야 한다 | 서버에만 존재하는 상태가 하나 더 생긴다 |
| 매 배포 CloudFront 전체 무효화(`/*`) | 빌드 설정을 고치지 않아도 된다 | 요청을 빠뜨려도 드러나지 않는다. 코드 분할 청크가 여럿이라 대상이 많다 | 실패가 조용하다 |
| CodeDeploy 로드 밸런서 연동 | 배포 중 트래픽을 자동으로 차단·복구한다 | 대상 그룹 구성이 어긋나면 `AllowTraffic`에서 오래 대기한다 | 단일 인스턴스에서 얻는 것이 적고 실패 시 원인 파악이 어렵다 |
| 가비아 웹 포워딩으로 apex 리다이렉트 | 콘솔 설정 하나로 끝난다 | `@`뿐 아니라 `www`에도 A 레코드를 만들어 CloudFront CNAME을 밀어낸다 | 사이트 전체가 뜨지 않게 된다 |
| apex 전용 리다이렉트 배포 구성 | apex 유입을 살릴 수 있다 | 전용 S3 버킷·CloudFront 배포·인증서 재발급이 필요하다 | 지울 수 없는 리소스가 둘 늘어난다 |

## 결과와 트레이드오프

### 환경 분리 (2026-08-15 추가)

이 구조 위에 dev 환경을 얹었다. **결정을 바꾸지 않고 같은 구조를 한 벌 더 만든 것**이므로 새 ADR로 나누지 않는다.

| 환경 | 브랜치 | 백엔드 | 프론트엔드 |
| --- | --- | --- | --- |
| prod | `main` | `api.jachwi-sunbae.kr` | `www.jachwi-sunbae.kr` |
| dev | `develop` | `dev-api.jachwi-sunbae.kr` | `dev.jachwi-sunbae.kr` |

새로 만든 것은 EC2 한 대와 CloudFront 하나뿐이다. RDS·ALB·WAF·S3는 공유한다. 따로 만들면 RDS +$15, ALB +$17이 더 든다.

격리는 여섯 계층에서 이뤄진다.

| 계층 | 나누는 기준 |
| --- | --- |
| 배포 대상 | EC2 태그 `DeployTarget` |
| 요청 라우팅 | ALB 호스트 헤더 규칙 |
| 데이터 | RDS 스키마 |
| 사진 | S3 접두사 |
| 프론트 정적 파일 | CloudFront origin path |
| 토큰 | `JWT_SECRET_BASE64` |

**RDS를 공유하는 대가를 감수한다.** dev 부하가 prod 성능에 영향을 줄 수 있다. `db.t4g.micro`는 1GB에 vCPU 2개다. 문제가 되면 분리한다.

**dev EC2는 `t4g.micro`다.** 예산 여유가 $3뿐이라 `t4g.small`을 쓸 수 없다. 실측 여유는 296MB이며 스왑 2GB를 붙였다.

### 기대하는 결과

- `main` 병합이 검증·빌드·배포·기동 확인으로 이어진다. 사람이 배포 명령을 실행하지 않는다.
- 배포 지식이 한 사람에게 묶이지 않는다. 절차와 판단 근거가 저장소 문서에 있다.
- 기동하지 못하는 리비전은 배포 성공으로 기록되지 않고 자동으로 되돌아간다.
- 빌드 결과가 사람과 환경에 따라 달라지지 않는다.
- 배포 후 접속하면 항상 최신 번들이 온다.
- 장기 액세스 키가 저장소·서버·CI 어디에도 없다.

### 감수하는 비용과 한계

- **빌드 정의가 저장소 밖에 있다.** CodePipeline `Commands`의 명령은 콘솔에 있어 코드 리뷰를 거치지 않고 변경 이력도 남지 않는다. 문서와 어긋날 수 있다.
- **운영 비밀의 변경 이력이 남지 않는다.** 값을 바꾸려면 사람이 서버에 접속해야 하고, 인스턴스를 다시 만들면 파일을 다시 만들어야 한다. 비밀이 서버 디스크에 평문으로 남는다.
- **무중단 배포가 아니다.** `systemctl restart` 중 짧은 다운타임이 있다.
- **단일 인스턴스다.** EC2 한 대가 죽으면 서비스가 멈춘다.
- **운영 포트가 로컬과 다르다.** 로컬 8080, 운영 80이다. 보안 그룹을 바꿀 수 없어 나온 결과다.
- **apex 도메인이 동작하지 않는다.** 도메인을 그대로 입력한 사용자는 아무 곳에도 닿지 않는다.
- **사진 저장소가 실제로는 비공개가 아니다.** 공용 버킷 정책이 `Principal: *`로 `s3:GetObject`를 허용한다. 객체 키가 UUID라 추측은 어렵고 목록 조회도 막혀 있지만, 접근 제어가 아니라 추측 난이도에 기대는 상태다. [ADR-0006](0006-use-private-s3-compatible-photo-storage.md)의 전제와 어긋난다. 공용 버킷이라 팀이 바꿀 수 없고 서비스 동작에는 영향이 없어 현재 구성을 그대로 둔다.
- **모니터링이 없다.** 배포 성공 여부는 확인하지만 운영 중 지표는 수집하지 않는다.
- **자동 롤백이 파이프라인 계층에만 있다.** 파이프라인 밖에서 수동 배포하면 롤백이 동작하지 않는다. 롤백 실행에도 초록불이 뜨므로 실행 목록만 보면 성공으로 읽힌다.
- **WAF 연결을 확인할 수 없다.** IAM 사용자에게 조회 권한이 없다. 연결 작업은 오류 없이 끝났고 요청도 통과한다.

## 검증 방법

2026-08-15에 외부에서 확인했다.

- `https://api.jachwi-sunbae.kr/actuator/health`가 `{"status":"UP"}`을 반환한다.
- `http://api.jachwi-sunbae.kr`이 HTTPS로 301 리다이렉트된다.
- `https://www.jachwi-sunbae.kr`과 내부 라우트 `/properties`가 모두 200을 반환한다. SPA 폴백이 동작한다.
- 운영 도메인 Origin으로 요청하면 `access-control-allow-origin`이 운영 값으로 온다.
- `main` 병합으로 두 파이프라인이 웹훅에 의해 자동 실행된다.
- 구글 로그인 → 매물 등록 → 사진 업로드가 동작한다. 사진은 `s3://techcourse-project-2026/jachwi-sunbae/members/...`에 쌓인다.
- 첫 기동에서 Flyway가 V1~V4를 자동 적용했고 이후 기동에서는 추가 적용이 없다.
- 배포 실패 시 `ValidateService`에서 중단되고 자동 롤백된다. 구축 중 실제로 여러 번 확인했다.

## 재검토 조건

- IAM Role이나 액세스 키를 만들 수 있게 되거나, 팀 전용 비밀 저장소를 쓸 수 있게 된다.
- `codebuild-project` role이 파이프라인 산출물을 읽을 수 있게 된다. 빌드 정의를 저장소로 되돌린다.
- 인스턴스가 둘 이상이 되거나 배포 중 다운타임을 감당할 수 없게 된다.
