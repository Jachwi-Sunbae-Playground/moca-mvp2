# ADR-0003: MVP에 레이어드 구조와 JDBC Template을 사용한다

- 상태: 승인
- 결정일: 2026-08-04
- 참여자: 자취선배 백엔드 팀

## 맥락

초기 MVP는 빠르게 사용자 가설을 검증해야 하며 아직 복잡한 연관관계와 도메인 규칙이 충분히 드러나지 않았다. JPA와 헥사고날 아키텍처를 먼저 적용하면 미래 확장에는 유리할 수 있지만, 현재 문제보다 매핑 객체와 인터페이스 수가 먼저 늘어날 수 있다.

## 결정

- 최상위 패키지는 업무 도메인별로 나눈다.
- 각 도메인 안에서 `controller`, `service`, `repository`, `domain`, `dto` 레이어를 사용한다.
- 의존 방향은 `controller → service → repository`를 기본으로 한다.
- 데이터 접근은 Spring JDBC의 `JdbcTemplate`을 사용한다.
- JPA와 헥사고날 아키텍처는 1차 MVP에서 사용하지 않는다.
- Controller의 Request/Response DTO와 Service의 Command/Result를 분리할 수 있는 경계를 둔다.
- Command와 Result는 서비스의 공개 유스케이스 경계에서 필요할 때 사용하며 모양이 같은 DTO를 기계적으로 복제하지 않는다.
- 도메인 객체와 데이터베이스 행 매핑 객체의 분리는 실제 도메인 복잡도가 드러났을 때 다시 결정한다.

## 판단 질문과 현재 답변

| 질문 | 현재 답변 |
| --- | --- |
| 핵심 도메인에 복잡한 비즈니스 규칙이 존재하는가 | 아직 충분히 발견되지 않았다 |
| 현재 기능은 CRUD 중심인가, 도메인 판단 중심인가 | 초기 MVP는 CRUD와 단순 판단 비중이 높을 것으로 예상한다 |
| Domain과 영속 객체 사이의 변환 비용을 감수할 수 있는가 | 필요성이 확인되기 전에는 감수하지 않는다 |
| 영속 기술과 독립적인 Domain 단위 테스트가 필요한가 | 복잡한 도메인 규칙이 생기는 시점에 필요성을 재평가한다 |
| 팀이 많은 포트와 어댑터 클래스를 일관되게 이해할 수 있는가 | 현재는 단순한 레이어드 구조가 공통 이해에 유리하다 |
| 향후 구조 변경에 대비할 수 있는가 | HTTP DTO와 서비스 입출력 경계를 분리해 전환 지점을 남긴다 |

## 검토한 대안

| 대안 | 장점 | 우려 | 선택하지 않은 이유 |
| --- | --- | --- | --- |
| JPA | 객체 중심 변경 감지, 연관관계 매핑, 반복 SQL 감소 | 숨은 쿼리, N+1, 영속성 컨텍스트 학습 비용 | 현재 모델 복잡도에서 이점이 아직 확인되지 않았다 |
| 처음부터 헥사고날 아키텍처 | 외부 기술과 핵심 로직의 의존 방향을 강하게 통제한다 | 포트, 어댑터, 변환 객체와 클래스 수가 증가한다 | MVP 기능 규모에 비해 구조 비용이 크다 |
| 순수 Domain과 영속 객체 완전 분리 | 도메인 테스트와 영속 기술 교체가 쉽다 | 변환 코드와 중복 모델이 늘어난다 | 복잡한 도메인 규칙이 확인되기 전에는 비용이 앞선다 |
| Controller DTO를 Service까지 전달 | 객체 수가 적고 구현이 빠르다 | Service가 HTTP 입력 계약에 결합된다 | 향후 구조 변경과 다른 진입점 추가 비용이 커진다 |

## 결과와 트레이드오프

### 기대하는 결과

- 팀원이 짧은 시간 안에 코드 위치와 의존 방향을 이해한다.
- SQL과 데이터 접근 동작을 명시적으로 확인한다.
- 서비스 경계를 유지해 향후 헥사고날 구조로 이동할 여지를 남긴다.

### 감수하는 비용과 한계

- SQL, RowMapper, 키 생성과 조회 코드를 직접 작성해야 한다.
- 도메인 객체가 영속성 구조에 가까워질 수 있다.
- 복잡한 관계와 상태 변경이 늘면 Service와 Repository가 비대해질 수 있다.
- 구조 전환 시 패키지 이동과 인터페이스 추출 작업이 필요하다.

## 검증 방법

- 새로운 기능을 구현할 때 레이어 의존 방향을 코드 리뷰에서 확인한다.
- Command와 Result가 API DTO 복제만을 위해 만들어지지 않았는지 확인한다.
- 반복 SQL, 매핑 중복, 도메인 테스트 어려움을 회고에서 기록한다.

## 재검토 조건

- 연관관계와 조회 조합이 복잡해져 수동 매핑 비용이 반복된다.
- 엔티티 생명주기와 상태 전이 규칙이 핵심 복잡도가 된다.
- 동일 유스케이스에 Web 이외의 입력 또는 DB 이외의 출력 어댑터가 필요하다.
- 외부 시스템 교체나 테스트를 위해 포트 분리 필요성이 명확해진다.
- 도메인 규칙을 영속 기술 없이 독립적으로 테스트할 필요가 커진다.
