# ADR-0002: 백엔드 런타임과 빌드 도구를 선택한다

- 상태: 승인
- 결정일: 2026-08-04
- 참여자: 자취선배 백엔드 팀

## 맥락

Spring Initializr의 기본 선택은 Spring Boot 4.1이었지만, 팀은 짧은 MVP 기간 안에 환경 문제보다 사용자 문제와 협업에 집중해야 한다. 최신 버전이라는 이유만으로 선택하지 않고 팀 경험, 생태계 호환성, 학습 비용을 함께 고려했다.

## 결정

- Java 21을 사용한다.
- Spring Boot 3.5 계열을 선택하고 초기 버전을 `3.5.16`으로 고정한다.
- Gradle Wrapper를 사용하고 Gradle `8.14.3`으로 고정한다.
- Spring Web, Validation, JDBC, Actuator, springdoc-openapi를 기본 의존성으로 사용한다.
- Lombok은 사용하지 않는다.

## 근거

| 선택 | 근거 |
| --- | --- |
| Java 21 | 장기 지원 버전이며 팀이 익숙하고 Spring Boot 3.5와 안정적으로 사용할 수 있다 |
| Spring Boot 3.5 | 4.x보다 팀 경험과 라이브러리 사례가 충분해 초기 호환성 위험이 작다 |
| Gradle Wrapper | 팀원이 Gradle을 별도로 설치하지 않아도 같은 버전으로 빌드할 수 있다 |
| Actuator | 실행 환경 재현 시 애플리케이션과 DB 연결 상태를 공통 주소로 확인할 수 있다 |
| springdoc-openapi | 구현된 API 계약을 Swagger UI와 OpenAPI 형식으로 확인할 수 있다 |
| Lombok 미사용 | 생성 코드와 IDE 플러그인에 의존하지 않고 Java 코드의 동작을 명시적으로 유지한다 |

## 검토한 대안

| 대안 | 장점 | 우려 | 선택하지 않은 이유 |
| --- | --- | --- | --- |
| Spring Boot 4.1 | 최신 기능과 더 긴 향후 사용 기간을 기대할 수 있다 | 메이저 버전 변경에 따른 학습, 라이브러리 호환성, 사례 부족 | MVP에서 얻는 이점보다 전환 위험이 크다고 판단했다 |
| Java 17 | 매우 안정적이고 사례가 많다 | 최신 언어 기능과 향후 업그레이드 여지가 줄어든다 | 팀이 Java 21을 사용할 수 있어 낮출 이유가 없다 |
| 더 최신 Java LTS | 더 최신 기능과 긴 지원 기간을 기대할 수 있다 | 팀 경험과 기존 교육 환경의 차이가 커진다 | Java 21이 안정성과 학습 비용의 균형이 좋다 |
| Maven | 설정이 명시적이고 사례가 많다 | 팀의 기존 Gradle 경험을 활용하지 못한다 | 팀이 익숙한 Gradle이 초기 생산성에 유리하다 |
| Lombok 사용 | 반복 코드를 줄일 수 있다 | 과도한 애너테이션과 숨은 생성 코드가 모델 의도를 흐릴 수 있다 | MVP에서는 명시성과 공통 이해를 우선한다 |

## 결과와 트레이드오프

### 기대하는 결과

- 모든 팀원이 동일한 Java와 Gradle 기준으로 실행한다.
- 새 메이저 프레임워크 학습보다 제품 개발에 집중한다.
- 코드 생성 도구 없이 클래스의 생성과 변경 의도를 직접 확인한다.

### 감수하는 비용과 한계

- Spring Boot 4.x 도입은 이후 별도 마이그레이션이 필요하다.
- Lombok을 사용하지 않아 생성자와 접근자 같은 반복 코드가 늘어날 수 있다.
- OpenAPI는 구현 이후 자동 생성되므로 개발 전 API 합의 문서를 완전히 대체하지 않는다.
- 운영 프로필과 배포 환경은 아직 구성하지 않았다.

## 검증 방법

- `./gradlew --version`에서 Java 21과 Gradle 8.14.3을 확인한다.
- `./gradlew clean build`가 성공하는지 확인한다.
- Actuator와 OpenAPI 주소에 접근할 수 있는지 확인한다.

## 재검토 조건

- 필수 라이브러리가 Spring Boot 3.5 지원을 종료한다.
- 보안 및 유지보수 정책상 Spring Boot 4.x 전환이 필요하다.
- 반복 코드가 리뷰와 개발 속도에 실제 병목을 만든다는 근거가 쌓인다.
