# 시스템 개요

- 상태: 초안
- 갱신 조건: 외부 시스템, 인증, 배포 환경 또는 주요 데이터 흐름이 추가될 때
- 문서 성격: 파생
- 대조 대상: 실제 구성 요소, [배포 아키텍처 설계](../../../docs/operations/deployment-architecture.md)

## 현재 경계

```text
사용자
  ↓
프론트엔드(React SPA) ─ CloudFront ─ S3
  ├─ Google OAuth 2.0 Authorization Code + PKCE + nonce
  ↓ HTTPS/JSON + Authorization: Bearer
진입 계층 ─ WAF ─ ALB(HTTPS 종료)
  ↓ HTTP
백엔드(Spring Boot, EC2)
  ├─ HTTPS ─ Google token endpoint·JWK
  ├─ JDBC ─ MySQL(RDS)
  └─ S3 API ─ S3 호환 객체 저장소
```

- 백엔드는 사용자 요청을 처리하고 비즈니스 규칙과 데이터 저장을 담당한다.
- MySQL 접근은 `JdbcTemplate`을 사용한다.
- 로컬 MySQL은 Docker Compose, 테스트 MySQL은 Testcontainers로 실행한다.
- 프론트엔드는 Google callback의 state를 확인한 뒤 authorization code, PKCE code verifier, nonce와 redirect URI를 백엔드에 전달한다.
- 백엔드는 Google ID Token의 서명과 claim을 검증하고 내부 회원을 생성하거나 갱신한다.
- 백엔드는 내부 `memberId`를 subject로 가진 HS256 JWT Access Token을 발급한다.
- 보호 API는 서버 세션 없이 Access Token을 검증하며 인증 회원 ID를 애플리케이션 계층에 전달한다.
- 매물 API는 인증 회원 ID를 모든 조회·변경 SQL의 소유권 조건으로 사용한다.
- 사용자는 이름·보증금·월세·발견 경로가 있는 매물을 여러 개 등록하고 검색·조회·수정·삭제하며 매물 단위 메모를 저장할 수 있다.
- 사진 바이너리는 비공개 S3 호환 객체 저장소에 두고 MySQL에는 소유권·내부 키·형식·크기·체크섬·생성 시각만 저장한다.
- 사진 본문 API는 JWT 회원과 매물·사진 소유권을 확인한 뒤 원본 객체를 스트리밍하며 저장소 URL을 노출하지 않는다.
- 외부 사진 업로드는 DB 트랜잭션 밖에서 수행하고 DB 저장 실패 시 동기 보상 삭제한다. 사진·매물 삭제는 외부 객체 삭제 성공 뒤 짧은 DB 삭제 트랜잭션을 실행한다.
- 매물 목록은 최근 활동 시각으로 정렬하며 현재 활동에는 매물 생성·기본 정보 변경·메모 저장·사진 등록·삭제·활성 체크리스트 변경·방문 시작·항목 저장·최초 완료가 포함된다.
- 사용자는 세 단계의 제공 체크 항목과 주거 유형별 시작 프리셋을 조회하고, 같은 단계 체크리스트를 여러 개 생성·조회·전체 변경·삭제할 수 있다. 직접 작성한 CUSTOM 질문은 현재 체크리스트 안에만 저장하고 제공 검색·프리셋으로 확산하지 않는다.
- 회원 체크리스트의 이름과 PROVIDED·CUSTOM 혼합 순서는 MySQL에 원자적으로 저장한다. 전체 변경은 유지 항목의 로컬 ID를 보존하고 legacy 요청이 CUSTOM을 삭제할 위험이 있으면 409로 차단한다. 회원은 매물의 세 단계마다 현재 체크리스트를 하나씩 연결하고 같은 체크리스트를 여러 매물에서 재사용할 수 있다.
- 활성 연결은 이름과 항목을 복제하지 않는 live 참조다. 방문을 시작하면 현재 1~3개 활성 체크리스트의 이름·단계·origin·출처·질문·안내·순서를 MySQL의 별도 방문 스냅샷으로 원자적으로 복제한다.
- 원본 체크리스트 변경·교체·해제·삭제와 기준 항목 비활성화는 과거 방문 구조를 바꾸지 않는다. 체크리스트·로컬 항목 삭제는 과거 출처 ID만 NULL로 만들고 origin·질문·안내·순서는 보존하며 매물 삭제는 방문·단계·항목을 cascade한다.
- 방문 항목은 상태와 인라인 메모를 값·version·저장 시각이 분리된 두 채널로 저장한다. 상태는 `expectedStatusVersion`, 메모는 `expectedMemoVersion` 조건부 한 행 UPDATE를 사용해 한 채널의 저장이 다른 채널을 덮어쓰지 않는다. 완료 뒤에도 두 채널을 수정할 수 있고 최초 완료 시각은 유지한다.
- 매물 목록·상세는 가장 최근 시작한 방문과 저장 상태 기반 집계를 한 SQL 경계에서 조회한다. 과거 방문 수정은 매물 최근 활동에는 반영하지만 최근 방문 선택은 바꾸지 않는다.
- 방문 시작·상태 저장·인라인 메모 저장·최초 완료와 서로 다른 두 매물의 완료 달성은 구조화 로그로 관찰한다. 인라인 메모의 본문·길이·해시는 기록하지 않는다. 전용 이벤트 테이블·브로커·Outbox는 사용하지 않으며 관찰 실패는 이미 커밋된 요청을 실패로 바꾸지 않는다.
- Google Access Token과 ID Token은 자취선배 인증에 재사용하거나 저장하지 않는다.
- Google 통신 실패는 로그인에만 영향을 주며 이미 발급된 자취선배 Access Token 검증은 Google에 의존하지 않는다.
- JVM, JDBC 세션과 MySQL 컨테이너는 UTC를 사용하고 API 시간 모델은 `Instant`를 기준으로 한다.
- 매물 상세는 현재 활성 체크리스트의 단계·ID·최신 이름·항목 수, 최근 방문 요약과 전체 방문 수를 반환한다.
- 프론트엔드는 정적 SPA이므로 S3에 올리고 CloudFront로 서빙한다. 백엔드와 별도 파이프라인으로 배포해 한쪽 실패가 다른 쪽을 막지 않게 한다.
- 백엔드는 EC2에서 systemd로 실행하며 ALB가 HTTPS를 종료하고 HTTP로 전달한다. 배포는 `main` 병합에서 자동으로 이어진다([ADR-0008](../adr/0008-deploy-with-aws-native-pipeline.md), [배포](../operations/deployment.md)).
- 사진 저장소는 여러 팀이 공유하는 S3 버킷의 팀 접두사를 사용한다. 이 버킷은 정책상 공개 읽기이므로 [ADR-0006](../adr/0006-use-private-s3-compatible-photo-storage.md)이 전제한 비공개 저장소가 실제로는 성립하지 않는다. 소유권 확인과 URL 비노출은 애플리케이션 계층에서 유지한다.
- 외부 모니터링의 구체적인 구성은 아직 결정하지 않았다.

새 구성 요소를 추가할 때 책임, 통신 방식, 실패 영향과 소유 팀을 함께 기록한다.
